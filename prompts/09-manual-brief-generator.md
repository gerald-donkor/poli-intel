# 09 — Manual brief generator (with the hallucination-guard pass)

## Goal

Staff paste a policy document, pick a brief type and audience, choose evidence from the library, and receive a drafted brief — generated by Gemini 3.6 Flash, fact-checked before it is persisted as reviewable, and stored as `Brief` + `BriefVersion` + `HallucinationFlag` records.

This is the first Gemini *generation* path in the codebase. Everything so far has been embedding only.

**In scope**

- Generation config, the versioned system prompt, audience profiles, brief-type length targets
- The AI-layer generation call and its Zod-validated structured output
- The hallucination-guard fact-check pass, running **before** the draft persists as reviewable
- A `BriefGeneration` attempt record (new model + migration) so a failed generation is a real, queryable outcome
- `/briefs/new` — the generation form: pasted policy text, brief type, audience, evidence picker
- `/briefs` — a real brief list by status, replacing the placeholder
- `/briefs/[id]` — a **read-only** draft view rendering the body, the citation list, and the guard-flag panel
- The three-stage generation stepper, driven by real completed work

**Explicitly out of scope — do not build any of it here**

- Tiptap, the citation-chip Node, the flag Mark, editing a draft (prompt 10, with `tiptap-editor` + `hallucination-guard` together per §9.9)
- Word / PDF / Google Docs export (§16.8)
- The audience switcher and re-generation (§16.4)
- Twi translation assist (§16.6)
- The Evidence Matcher: no signal input, no auto-matching from the pasted document, no cross-encoder rerank, no gap record (§15.1). Evidence selection here is manual.
- Brief approval / status transitions and the flag-dismissal action. Flags are **created and rendered** here; resolving them and the approval refusal ship with the editor and review work. Say so in the UI rather than shipping a dead button.

## Decisions and assumptions

1. **Sequential Server Actions, not Inngest, and not a faked stepper.** The three stages are three real, separately-awaited Server Actions driven by the client:
   - `startBriefGeneration` — authorise, validate, load and re-gate the selected evidence, write a `BriefGeneration` row at `retrieving` → `drafting`. This is "Reading evidence" and it does real work.
   - `draftBriefAction(generationId)` — the Gemini generation call; stores the validated draft **on the attempt row**, not as a `BriefVersion`. This is "Drafting".
   - `verifyBriefAction(generationId)` — the fact-check pass, then the transaction that creates `Brief` + `BriefEvidence` + `BriefVersion` + flags. This is "Verifying citations".

   Rationale: `gemini-integration` forbids faking a stage that is not running, and a single awaited action cannot report intermediate progress without streaming. Inngest is not used because generation is on-demand and interactive (§5.1), not scheduled or event-triggered, and an awaited Server Action is not the fire-and-forget promise §14.1 prohibits. The draft survives a rate limit because it is already on the attempt row before stage 3.

   **§9.1 ordering is preserved and is the reason for the split shape:** nothing reachable as a reviewable brief exists until `verifyBriefAction` commits. A `BriefGeneration` in `drafting` state is an attempt, not a brief; it must not appear in the brief list and must not be loadable at `/briefs/[id]`.

2. **Evidence selection is manual.** The officer searches the library (existing `lib/evidence/search.ts`, existing branded `SearchQuery`) and picks up to `GENERATION_EVIDENCE_CONTEXT_SIZE` (8) items. No new embedding door is opened for the pasted policy text — auto-matching arrives with the Evidence Matcher. `BriefEvidence.relevanceScore` stays `null` for manually chosen items; do not invent a score.

3. **No LangChain.** A single generation call and a single verification call do not need an orchestration layer. LangChain lands with the Matcher's retrieval chain (§15.6). Do not add the dependency here.

4. **Anchors are character offsets into `bodyText` for now.** `BriefVersion.documentJson` stays `null` in this prompt. A flag's `anchorFrom`/`anchorTo` are the offsets of `claimText` within `bodyText`, found by exact match; when the claim cannot be located exactly, store `0`/`0` and rely on `claimText`, which the schema already names as the re-anchoring key. Prompt 10 maps these to Tiptap positions when it builds the document. State this in a comment on the mapping function so the editor prompt does not have to rediscover it.

5. **The pasted policy document is not evidence and must not become evidence.** It is an external policy text the officer supplies, and it goes to Gemini as signal context (spec §3.4). It is never written to `evidence_item`, never embedded, never stored beyond the `BriefGeneration` row. The form carries an explicit inline notice: *public policy documents only — do not paste community-sourced or unpublished internal material.* A character cap (`BRIEF_POLICY_TEXT_MAX_CHARS`) bounds it.

6. **Model IDs are verified, not remembered.** `gemini-3.6-flash` and the structured-output config field names must be confirmed against `node_modules/@google/genai` and the live docs during implementation. If the ID or the config surface differs from what `gemini-integration` records, correct the skill in the same change rather than working around it.

7. **`PROMPT_VERSION` is a const in the prompt module** and is written to `BriefVersion.promptVersion` alongside `generatingModel`. Bump it by hand whenever the system prompt text changes.

## Implementation requirements

### Config (`lib/ai/config.ts`)

Add, with the same commenting discipline as the embedding block: `GENERATION_MODEL`, `GENERATION_TEMPERATURE = 0.3`, `GENERATION_MAX_OUTPUT_TOKENS = 4000`, `GENERATION_EVIDENCE_CONTEXT_SIZE = 8`, `GENERATION_EVIDENCE_EXCERPT_CHARS`, `BRIEF_POLICY_TEXT_MAX_CHARS`, `GENERATION_INVALID_OUTPUT_RETRIES = 1`. No number from this list appears inline anywhere else.

### The gate

`lib/ai/generate-brief.ts` and `lib/ai/fact-check.ts` each accept **only** already-partitioned eligible items — mirror the branded-door discipline of `query-embedding.ts` so an ineligible item cannot be handed in. `startBriefGeneration` calls `partitionByClassification` on the selected items **after re-reading them from the database** (a classification can change between picking and generating) and:

- refuses the whole generation if **any** selected item is refused, naming the refused items by title and classification (never their body text) with a link to the classification queue;
- the evidence picker only ever lists `ELIGIBLE_EVIDENCE_WHERE` rows, so this should be rare — but it is the enforcement point, and the picker is presentation.

Log ids, classifications, counts, timings. Never prompt text, never completion text, never evidence body text (§7.6, §13.9).

### Generation call

- Structured output validated with Zod before any use. Shape: `{ title, executiveSummary, context, findings: [{ heading, body, citations: [evidenceItemId] }], recommendations: [{ ask, decisionMaker }], implementationPathway, aboutTropenbos, statedGaps: string[] }`. Adjust field names to what reads well, but keep citations as evidence-item ids so the citation list can resolve them.
- Assemble `bodyText` from the validated object in the standard §16.2 order.
- Invalid structured output → retry once → then record the attempt as `failed` with reason `invalid_output`. Never persist unvalidated output, no cast past a parse failure, no `any`.
- 429 → the `gemini-integration` degradation contract: a slate/olive `Alert` with retry timing, the attempt row preserved, the pasted text and selections preserved. Never a destructive variant, never a generic toast.
- The prompt carries the gap instruction: where no strong evidence match exists, state the gap explicitly — never unsourced filler (§9.8). Stated gaps render as their own section in the draft view.
- Evidence context: the 8 items as structured context with source metadata (title, authors, year, country, impact area, source type, citation key) and a bounded excerpt per item. Never unbounded context (§13.7).

### Fact-check pass

- A separate Gemini call receiving the generated draft and **the same evidence context that was passed to the generator** — the recorded set, not the library.
- Returns, Zod-validated: per claim, `claimText` (verbatim from the draft), `supported: boolean`, `reason: FlagReason` when unsupported, `checkedEvidenceItemIds`.
- Only unsupported claims become `HallucinationFlag` rows, `status: open`, on the new `BriefVersion`, with anchors per decision 4.
- Same retry-once → `failed` (`invalid_output`) rule. A failed verification means **no reviewable brief is created** — the attempt is failed and the officer is told so plainly.
- The pass runs before persistence. There must be no code path that writes a `Brief` without it having run.

### Persistence

One transaction: `Brief` (status `draft`, `currentVersion: 1`, `generatedAt`, `createdById`) + `BriefEvidence` rows + `BriefVersion` (version 1, `bodyText`, `generatingModel`, `promptVersion`, `createdById`) + `HallucinationFlag` rows. Link the `BriefGeneration` row to the created brief and mark it `complete`.

### Authorisation

`canGenerateBrief` inside every one of the three actions — not just the first. Stages 2 and 3 additionally verify the attempt belongs to the calling user. Field Officer and Research Officer are refused with the established `unauthorised(...)` refusal.

### UI

Mobile-first, unprefixed classes are the phone layout; `tablet:` / `laptop:` / `desktop:` add columns (§11.15). No fixed pixel page widths.

- **`/briefs/new`** — single column on phones; on `laptop:` the form left, evidence picker right. Policy-text textarea with the governance notice and a live character count against the cap. Brief type and audience as shadcn `Select` / `RadioGroup`, each showing its length target and framing emphasis so the choice is informed. Evidence picker reuses library search, shows classification badges, caps selection at 8 with the count visible.
- **Stepper** — custom, built from `Progress` + a manual step list (design-system line 240). Three named stages: Reading evidence → Drafting → Verifying citations. Completed stages fill visibly; the active label breathes 0.85–1.0 opacity over 2s — the only looping animation in the product. **No indeterminate spinner anywhere.** `prefers-reduced-motion` gets the settled state.
- **`/briefs/[id]`** — read-only. Generated prose in the **sans**; quoted source excerpts and citations in **Source Serif 4** (`font-serif text-quote text-ink border-l-2 border-accent pl-4`). Breaking this distinction defeats the design.
- **Flag panel** — slate: `bg-watch-surface border border-watch-border rounded-card p-4 text-watch-ink`, shadcn `Alert` with a custom slate variant, **never `destructive`**. Round 16px icon, 2px stroke `#496375`, filled centre dot. `flag-pulse` 900ms, **once**, settling to a steady 2px underline; no loop, no re-fire on re-render. Never red, never a blink, never an error toast. Copy says the claim is *not traceable to the supplied evidence* — never "incorrect", never anything implying the system verified or approved something (§8.8).
- The flag panel promotes above the fold at small breakpoints rather than being dropped.
- Approval is not built here; the draft view states that approval and flag resolution arrive with the review work rather than showing a disabled control with no action behind it.
- WCAG 2.1 AA: keyboard-navigable picker and stepper, ARIA labels on flag and classification badges, 4.5:1 minimum — verify any new pairing.

## Evidence classification impact

**Yes — this task is squarely inside the gate.** It touches `evidence-governance` call types **4 (generation)** and **8 (fact-check)**, the two most consequential ones, and it is the first generation path in the codebase.

- **Classifications involved:** only `public_published` may reach either call. `community_sourced` and `unpublished_internal` are refused.
- **Enforcement point:** `partitionByClassification` from `lib/governance/gate.ts`, called in `startBriefGeneration` (`app/(app)/briefs/new/actions.ts`) against items **re-read from the database at generation time**, not against ids trusted from the client. `lib/ai/generate-brief.ts` and `lib/ai/fact-check.ts` accept only the eligible half and expose no variant that takes raw evidence. The evidence picker additionally lists only `ELIGIBLE_EVIDENCE_WHERE` rows — presentation, not the control.
- **What happens to blocked items:** the generation is refused whole before any Gemini call. The officer sees the refused items by title and classification (never body text) with a link to `/evidence/queue`, and the existing classification-pending count remains the standing surface for the backlog. Refusal is returned as data in the action's result; it is never thrown away, never a silent skip.
- **Pasted policy text:** not evidence, never stored as evidence, never embedded — see decision 5, including the inline notice and the length cap.
- **No bypass** is added: no flag, no env var, no `force`, no dev branch, no anticipatory paid-tier path (§7.7).

## Hallucination-guard implications

**Yes — this task implements the guard for the first time.**

- Claim extraction, verification against the recorded evidence set, and flag creation all land here.
- Flags are stored as structured `HallucinationFlag` records against the `BriefVersion`, anchored by character offsets into `bodyText` plus `claimText` (decision 4) — not embedded in prose, not inferred at render time.
- Flag rendering is introduced, so the visual contract is restated exactly: **slate, gentle single 900ms pulse settling to a steady soft outline; never red, never a blink, never an alarm, never an error toast**; round 16px icon distinguishing a review flag from the square classification-pending glyph; settled state instantly under `prefers-reduced-motion`.
- What a flag blocks: nothing is blocked *in this prompt* because approval is not built here. The rule it will enforce — the approval Server Action re-reads flag state and refuses server-side while any flag is open (§9.5) — is already documented on `canApproveOrRejectBrief` and must not be weakened by anything written here. Do not add an approve control.
- Export is not built here, so §16.8's flag notice is not yet applicable.

## Security requirements

- `GOOGLE_GENERATIVE_AI_API_KEY` stays server-only; the new AI modules are `import "server-only"`.
- UI never imports the AI layer; it calls the Server Actions (§5.3).
- Every action authorises server-side before doing work; stages 2 and 3 verify attempt ownership.
- Zod schemas shared with React Hook Form for the form; no role predicate or authorisation logic in any client-visible schema (§10.10).
- No prompt, completion, or evidence body text in any log, error report, or analytics payload.
- No new environment variable is needed; if one turns out to be, add it to `.env.example` and the `AGENTS.md` §18 table in the same change.

## Acceptance criteria

1. An officer can paste a policy document, choose a brief type and audience, select up to 8 eligible evidence items, and receive a persisted draft at `/briefs/[id]`.
2. Selecting an item whose classification changed to non-`public_published` before generation refuses the whole run, names the item, and makes no Gemini call.
3. No `Brief` row can exist without the fact-check pass having run against it.
4. Unsupported claims appear as `HallucinationFlag` rows with `status: open`, anchored, and render in slate with a single pulse.
5. Invalid structured output retries exactly once, then the attempt is `failed` with reason `invalid_output` and is visible as such — never a partial save.
6. A 429 mid-run shows retry timing, preserves the pasted text, selections, and any already-generated draft, and is not a destructive alert.
7. The stepper's three stages correspond to work that actually ran; there is no indeterminate spinner in the flow.
8. Generated prose renders in the sans; quoted excerpts and citations in the serif.
9. A Research Officer and a Field Officer are both refused by the generation actions server-side, not merely by a hidden link.
10. `/briefs`, `/briefs/new`, and `/briefs/[id]` are legible with no horizontal page scroll at 390, 760, 1000, 1300, and 1600px.
11. No model ID, temperature, token cap, or context size appears outside `lib/ai/config.ts`.
